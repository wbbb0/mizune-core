# 上下文预算与历史压缩

路由预设 `tokenLimits.contextTokens` 表示**总上下文**，包含输入、输出预留与安全余量。它是模型能力之外的最终兜底上限，不是输入 Token 触发阈值。

每个实际请求候选独立计算：

- 总容量 = min(模型 contextTokens, 预设 contextTokens)。模型未声明容量时使用预设；预设默认 150000。
- 输出预留 = min(本次覆盖值或模型默认值, 模型 maxOutputTokens)。未指定时预留 min(4096, 总容量 / 4)。服务原生 extra 输出参数也参与预算，建议统一使用 defaults.maxOutputTokens。
- 安全余量 = min(1024, 总容量 × 2%，向上取整)。
- 可用输入 = min(模型 maxInputTokens, 总容量 − 输出预留 − 安全余量)。

不会因为输入增加而静默挤掉已预留的输出空间。无效配置或无法容纳的请求在发送前明确失败。容量估计是启发式估计，不等同于服务端 tokenizer；诊断日志与服务端 usage 应分别解释。

`requestTokenBudget.ts` 统一估计完整 messages、推理回放、工具调用、工具定义、媒体和消息协议开销。主模型、规划器、摘要器等均接受同一发送前检查；不会取不同角色或未使用候选模型容量的全局最小值。fallback 会重新按自己的容量准备和校验请求。

主生成链的 `generationRequestBudget.ts` 在完整请求超限时依次执行：

1. 使用现有工具观察策略缩短可回放的旧工具结果，保留要求原样回放的近期结果。
2. 由 HistoryCompressor 总结较早历史，重建请求中的摘要和历史部分，再次检查完整请求。

`tokenLimits.retainTokens` 是近期历史保留目标，不是精确截断数。自动压缩向完整用户轮次对齐，保护最近一轮和当前工具链。固定设定、当前输入或工具定义本身过大时会报预算不足；不会为了发送而把业务工具全部关闭，也不会截断当前工具结果。单轮仅尝试一次历史压缩，不循环重试。手动压缩仍支持显式指定保留消息数，包括零。

摘要器按实际候选模型的预算分块处理来源；切换备用模型时重新分块，独立预留输出，失败尝试不消费来源内容。成功切换后后续分块沿用备用候选链，避免反复请求已失败的首模型；一次最多 64 个分块。所有分块完成、结果非空且请求触发的摘要确有缩减后，才以历史 revision 校验提交。取消、模式切换、并发修改或摘要失败均不覆盖原历史。

摘要保存到原有 session.historySummary。原 transcript 保留，已纳入摘要的记录标记 `runtimeExcluded: true` / `runtimeExclusionReason: history_compressed`，不再送给模型。聊天页继续显示原消息，内部记录页标明已纳入摘要。用户仍可按单条、整组或截断操作将这些记录转为手动隐藏；压缩标记不等同于用户删除。角色档案、状态和存档结构不变。旧会话无需转换即可读取。

WebUI 在请求等待期间显示“正在压缩历史上下文”。`generation_request_budget` 日志只包含模型标识、总容量、输出预留、安全余量、压缩前后估算、工具缩减数和是否应用摘要，不包含内容。历史局部估算与上一请求的 usage 不再负责自动触发压缩。

## 旧配置迁移

旧 `tokenLimits.triggerTokens` 在文件读取边界迁移为 `contextTokens`，数值原样保留；两者同时存在时以新字段为准。运行时和配置编辑器仅使用新字段，编辑器保存后写回新格式。

也可以在部署前显式迁移文件（先备份再原子替换，保留 YAML 注释；不访问会话数据）：

```sh
node --import tsx scripts/migrate-context-budget.ts config/llm.routing-presets.yml
```

例如旧阈值 200000 变成总容量 200000 后，输入可用空间会扣除输出预留和安全余量，因此压缩会更早发生。这是新的总上下文语义。
