# 定时任务的运行与编辑边界

定时任务由 `ScheduledJobStore` 保存定义与运行状态，`Scheduler` 管理排程和当前调用，Croner 负责 Cron 表达式、时区和未来一次性任务的等待。内部 API 的数据编辑器与模型工具都通过同一个 store 修改记录，不能绕过 store 直接写表。

## 启动、重载和停止

`start()` 显式开启调度并加载现存任务；未启动或已经停止时，新建和启用只保存任务，等待下一次显式启动。`reloadFromStore()` 撤销旧排程并读取最新定义。同一任务 ID 在本进程中最多有一个正在执行的调用，重载或编辑产生的新排程会等它结束后再生效。

交互式工具调试 CLI 使用 `start({ loadExisting: false })`，只执行调试过程中明确新建或启用的任务，避免 `--use-instance-data` 加载并消费实例原有的任务。正式运行时使用默认启动方式。

`stop()` 撤销后续排程并使尚未触发的旧回调失效。它不取消已经交给 `onTrigger` 的外部工作，也不等待该工作结束。已经触发的工作仍可以记录最终结果，但不能重新启动已停止的排程。这是调度器的边界；应用退出时若要等待会话生成或外部发送完成，应由应用生命周期统一管理和等待这些工作，不能把 `stop()` 当作全部工作已结束的信号。

重载时仍在本进程运行的调用不属于“上次进程异常中断”。只有数据库记录为 `running`、本进程又没有对应活动调用时，才执行启动恢复：Cron 记录一次中断错误后重新排程；一次性任务移除，避免重复投递一个可能已经执行过的指令。这不能提供外部副作用的严格 exactly-once 保证。

## 配置和运行状态各自的归属

Scheduler 使用全局生命周期 epoch 和每次排程的对象身份，阻止停止或重载之前的异步回调重新注册定时器。Store 为现存记录维护进程内 identity 与 definition token：

- 新建记录取得新的 identity；删除同时回收 token，复用同一 ID 也不会取得原记录的执行归属。
- 名称、启用状态、计划、指令、目标会话和创建时间发生变化时，definition token 更新。单纯写入运行状态或更新时间不改变定义版本。
- 执行计划、指令、目标会话或创建时间发生变化时，旧运行快照清空，新定义从待执行状态开始。仅改名称或启用状态会保留正在执行的那次调用的状态。

这些 token 只用于进程内并发控制，不增加数据库字段，也不为已删除记录保留版本墓碑。

数据编辑器只提供任务定义表单，运行状态与更新时间作为只读详情显示。定义保存时，store 忽略草稿携带的旧 `state` 和 `updatedAtMs`，保留当前运行状态并生成更新时间；因此，即使用户在任务开始前打开了编辑窗口，稍后保存名称也不会把正在执行的任务还原成待执行状态。

运行开始和结束都通过 store 的原子 `transitionRuntime()` 入口读当前记录、检查归属、再修改状态列。完成回调不会整行写回旧快照。旧调用只有在记录 identity 与当前运行状态仍对应它时才能报告结果；连续失败自动停用和消费一次性任务，还要求 definition token 没有改变。因此，运行中禁用再启用任务，也不会让旧调用的第五次失败停用新的激活状态。

## 一次性任务与重复执行

未被编辑的一次性任务在成功或失败后移除。若执行期间只修改名称或切换启用状态，完成后保留最新记录及该次执行结果，`nextRunAtMs` 为 `null`；即使再次重载或启动，也不会重放已经消费过的那次执行。需要再次执行时，应新建任务或修改执行计划、指令、目标等执行定义。

若执行期间改了执行定义，旧调用的结果不会删除或覆盖新定义。新定义等待旧调用结束后按最新计划执行，不与同一 ID 的旧调用重叠。一次性任务的下次执行时间从当前 `schedule` 计算，不沿用旧定义留下的 `nextRunAtMs`。

未来一次性任务也由 Croner 等待，避免直接把超过 Node.js `setTimeout` 上限的毫秒值变成近乎立即触发的定时器。已经到期的任务通过事件循环触发，不阻塞整个调度器启动过程。
