# 新消息打断与插入

`conversation.interruptionMode` 可在全局或实例配置中设置，WebUI 配置编辑器提供同名枚举选项，默认 `after_tool`。

| 模式 | 运行中收到可打断的新消息 |
| --- | --- |
| `immediate`（直接打断） | 取消生成及剩余发送，保留已展示的部分回复，关闭未完成的工具记录；新消息按会话聚合等待设置进入下一轮。 |
| `after_tool`（工具调用后插入） | 立即作废未发送的旧回复；新消息进入 steer 队列，保留当前请求及工具结果，在下一次模型请求前按到达顺序一次性注入，继续当前回复。 |

“工具调用后”指当前工具批次完成后的模型请求边界，批次内并行工具都会先完成。请求尚未开始时可直接在请求前注入；已经发出的模型请求无法追加输入。无后续工具调用、达到轮次上限或本轮失败时，未消费消息提升为下一轮输入。已经进入发送阶段的新消息会取消剩余发送并排入下一轮；延迟等待会立即唤醒，下一轮无需等旧的模拟发送间隔结束。已发出或已进入 OneBot 发送接口的消息不撤回。

策略只作用于原本允许软打断的消息：私聊、WebUI 输入，以及群聊当前回复对象再次明确 @ bot。其他群成员的触发仍排队，普通群聊消息不新增模型调用。停止/重置等显式命令保持原语义。

## 输出取消与工具循环

输出队列使用独立的 `outboundAbortController`，不复用整轮 `responseAbortController`。收到可插话的新消息时取消输出信号，队列等待立即结束，旧片段及后续旧请求文本不再发送，未提交草稿清除。模型请求、工具和 mutation/response epoch 保持不变。

只有工具循环实际消费 steer 队列时才更新输出信号，并清空旧文本缓冲；新请求的输出可以继续投递。旧队列项在异步渲染之前捕获信号，不能误用新信号复活。若没有后续请求，保持旧输出禁用，由原有收尾流程把插话提升至下一轮。未发送文本不进入已投递历史；模型侧完整工具调用及结果仍保留。

## 历史与 WebUI

新消息接收时即记录并通过 SSE 展示；可见不代表已经被模型消费。待插入消息使用待处理 transcript 分组，在初始 prompt/replay 中排除，由工具循环入口单独消费，避免重复注入。消费后清除空闲的待处理分组引用，使其在后续轮次中作为正常历史保留；未消费时保留分组供下一轮使用。当前工具仍显示真实完成结果，不生成“被打断”占位结果。

Sessions 的会话调度面板说明两种语义，配置入口位于全局配置编辑器。模式变更随配置热重载生效，对后续收到的消息使用新策略。切回直接打断时，已经排队但尚未注入的补充消息先移入下一轮，保持到达顺序。

## 与 Codex 的区别

截至 2026-10-21 核对的官方资料，Codex 的 follow-up 支持 steer 当前运行或排队到下一轮；公开 App 设置文档没有解释名为“低延迟打断”的开关实现，不能直接认定其等同于本项目取消重开。

OpenAI Responses API 的原生 mid-turn steering 使用同一 WebSocket 上的 `response.steer`，服务端在当前输出项及已运行的托管工具结束后创建续接响应。原响应可标记 `incomplete` / `steered`；已经启动的工具不会被撤销。这需要模型与协议支持，不能视为普通 HTTP 请求 AbortController 的替代名称。

本项目 `immediate` 是客户端取消并重新编排；`after_tool` 是应用层工具循环边界注入，适用于现有模型适配器，不依赖原生 steering。本次没有实现 Responses WebSocket 原生 steering，也不宣称与 Codex App 内部实现完全一致。
